# 給執行 Agent 的任務提示詞：建置 Arc Sentinel MVP

> 權威來源（2026-09-16）。完整規格書為同批 `SPEC-v1.0-2026-09-16.md`。

你的任務是把 **Arc Sentinel**（一個開源、非託管、唯讀的 Arc 主網 Agent 金流監控服務）從零建置到能在 OCI Always Free VM 上跑起來，最終目標是符合 **Arc Microgrants** 補助的申請資格。

**在開始任何程式碼工作之前，先完整讀過同一批附件裡的 `arc-sentinel-oci-mvp-plan.md`。** 那份文件是完整規格書（架構、資料庫 Schema、API、規則引擎、測試計畫、部署流程、14 天排程），本提示詞不重複那些細節，只做三件事：(1) 把已經拍板定案、你不該重新討論的決策講清楚，(2) 定義憑證處理的鐵律，(3) 定義你遇到什麼狀況必須停下來問人類、不能自己假設。

---

## 1. 已經拍板、不要重新討論的決策

- **技術棧**：Python + FastAPI + PostgreSQL + Docker + GitHub Actions。不要換成別的語言或框架。
- **部署目標**：單台 OCI Always Free 的 Ampere A1 VM，**2 OCPU / 12GB**（不是網路上常看到的舊版 4 OCPU/24GB，這個額度已在 2026 年 6 月被下修）。所有資源規劃、容器數量、記憶體配置都要卡在這個預算內。
- **RPC 供應商**：主要用 **Alchemy**，備援用 **dRPC**。不要再花時間比較 QuickNode 或 Blockdaemon。
- **鏈與網路**：直接對接 **Arc Mainnet，chain ID 5042**。Arc 主網已於 2026-09-16 正式上線，第三方節點商（Alchemy／dRPC／QuickNode／Blockdaemon）的主網端點已公開可自助申請，**不要因為看到某份文件寫「mainnet 尚未開放」就退回 testnet-only 的設計**——那通常是指 Circle 自家直營端點 `rpc.mainnet.arc.io` 仍需憑證，跟第三方節點商是兩回事。
  - Alchemy 主網：`https://arc-mainnet.g.alchemy.com/v2/{API_KEY}`
  - dRPC 主網（備援）：`https://rpc.drpc.mainnet.arc.io`
  - Testnet（僅 CI 整合測試用，理由是免費水龍頭方便重複測試，不是因為主網不可用）：chain ID `5042002`，`https://arc-testnet.g.alchemy.com/v2/{API_KEY}`
- **金額欄位一律用 `Decimal`／SQL `NUMERIC`，禁止用 float。** USDC 原生記帳是 18 位小數，但 ERC-20 USDC 合約（`0x3600000000000000000000000000000000000000`）是 6 位小數，兩者不可混用同一欄位。
- **告警與預算判斷全部用確定性規則程式碼實作，不可用 LLM 判斷資金相關邏輯。** 規則清單見主規格書 §9。
- **這是唯讀、非託管服務**：不持有任何私鑰、不簽署任何交易、不代客保管或轉移資金。這條界線不可更動。
- **License：MIT。**
- **Dashboard：讀取端點（含首頁與 `/stats/network`）公開，寫入端點維持 API Key 保護。** 不需要額外做存取控制設計，照 §8 原規劃即可。
- **Circle CLI 唯讀整合：MVP 不做。** 只用鏈上資料實作 §9 的規則引擎，把 Circle CLI 整合寫進 README 的 Roadmap 段落即可，不要現在花時間實作。
- **告警訊息要人類可讀。** `alerts.message` 不要只存規則代號，要組成一句完整的中文或英文敘述（例如「Agent X 今天花了 $12.40，是每日 $10 預算的 124%」），這只是格式化既有的確定性計算結果，不算讓 LLM 做財務判斷，不違反上面的規則界線。
- **首頁 Dashboard 做一個簡單的單頁視覺化**（幾個關鍵數字＋一張折線圖），不要只回傳原始 JSON。Jinja2+HTMX 就夠，不要為此引入前端框架。

## 2. 憑證處理鐵律

判斷原則只有一句話：**只要這個值是拿去打「專案以外的真實系統」（RPC、未來可能整合的 Circle API），本機開發和正式環境必須用同一份真值；只要是純粹內部接線用的值（本機 DB 密碼、本機雜湊鹽值），本機測試時愛怎麼設都行。**

完整憑證清單、每個值該放 `.env` 還是 GitHub Secrets，請直接查主規格書的 §17 憑證總表，逐項照做。這裡只強調三個不可違反的規則：

1. `.env` 檔案（不論本機或 VM 上的）**永遠不進版控**，`.gitignore` 一定要蓋到。
2. 任何 API Key、密碼、SSH 私鑰，**你自己絕對不要把明文寫進程式碼、commit message、README 或任何會被公開 GitHub repo 看到的地方**。範例檔一律只放變數名稱（`.env.example`），不放真值。
3. VM 上的正式 `.env` 由部署流程（`deploy.yml` 的 SSH 步驟）用 GitHub Secrets 的值自動覆寫產生，你不需要、也不應該手動去 VM 上編輯它。

## 3. 遇到以下狀況，停下來問人類，不要自己假設繼續

| 狀況 | 為什麼你做不了 |
|---|---|
| 需要 Alchemy／dRPC 的 API Key | 需要人類註冊帳號、完成驗證 |
| 需要 OCI 帳號、VM 建立、區域選擇 | 需要人類開帳號並在 Console 操作（可能需要信用卡驗證） |
| 需要網域或 DuckDNS 子網域 | 需要人類註冊 |
| 需要 GitHub repo 的 Secrets 設定 | 你可以生成建議的 Secret 名稱清單，但實際填值需要人類在 GitHub 網頁上操作 |
| 需要送出一筆 Arc 主網真實 USDC 測試轉帳（Phase 7） | 牽涉真實資金與私鑰簽署，這是人類手動用錢包 App 做的事，你不能、也不該經手任何私鑰 |
| 部署用網域名稱（買網域 / DuckDNS 起步） | 需要人類註冊 |
| Phase 7 用哪一個人類擁有的錢包、金額多少 | 牽涉使用者個人資產，只有他能決定 |
| 任何會員讓你「代為保管使用者資金」或「自動簽署交易」的功能請求 | 超出本專案的非託管、唯讀範圍，一律回報並拒絕實作，不要為了「方便展示」而妥協這條界線 |

遇到上面任何一種狀況，直接停下並清楚說明你需要什麼、為什麼需要，不要用假值頂替後繼續往下寫，也不要自己去猜一個「合理」的答案。

## 4. 執行順序

依主規格書 §15「給執行 Agent 的任務指令包」的 Phase 0 → Phase 8 依序執行，一次做完一個 Phase 才進下一個。每個 Phase 做完後：

1. 對照該 Phase 的驗收標準自我檢查，**沒有達成就明確說明卡在哪裡，不要宣稱完成**。
2. 用 3-5 句話向使用者回報：做了什麼、驗證方式、下一步需要使用者做什麼（如果有的話）。
3. 如果某個 Phase 內部又分成子任務，你可以自行拆解，但不要跳過 Phase 順序（例如還沒完成 Phase 1 資料層就先動 Phase 4 的 API）。

## 5. 完成定義（Definition of Done）

整個專案「完成」的標準，是能對照主規格書 §3 的 Arc Microgrants 資格對照表逐項打勾：

- [ ] 服務部署在 Arc **正式主網**（chain 5042）且穩定運作（`/health` 連續 24 小時正常，落後區塊數維持個位數）
- [ ] GitHub Repo 公開，License 已選定
- [ ] README 完整（架構圖、Demo 連結、本機部署說明、專案動機、CI 測試徽章、一段說明「為什麼這不會被 Circle 自己內建功能取代」的商業定位段落）
- [ ] 已完成一次主網真實小額轉帳的端對端驗證（人類手動送出，Agent 驗證有被正確索引）
- [ ] 單元測試與整合測試皆通過，CI 綠燈
- [ ] 沒有任何私鑰或敏感憑證出現在版控歷史裡
- [ ] DoraHacks 的 BUIDL 提交表單本身已填寫完整（團隊簡介、連結、標籤），這是人類手動送件前的最後一步

達成以上全部項目之前，不要建議使用者去送出 Arc Microgrants 申請。
